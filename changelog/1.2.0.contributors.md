# 1.2.0 — notes for contributors

What changed about *working here*, as opposed to what changed for the chat
(see `1.2.0.en.md`). Short release, one feature, but it adds a whole surface
the project did not have: a browser client.

## There is a second client now

Until now the bot had exactly one way in — Telegram updates — and one web
endpoint, Microsoft's OAuth callback. `1.2.0` adds a **JSON API and a SPA**.

- **`bot/web/mini_*.py`** — the API. It is mounted on the *same* aiohttp
  application as the OAuth callback (`bot/web/oauth.py`), so one process and
  one listen port serve both. `mini_api.py` owns the routes and the
  personal/chat handlers, `mini_admin.py` the super-admin ones, `mini_me.py`
  / `mini_chat.py` the payload builders, `mini_auth.py` the signature check,
  `mini_avatars.py` the photo proxy, `mini_hltb.py` the HLTB lookup.
- **`webapp/`** — a Vite/React SPA. It is **never served by the bot
  process**: it is built to static files and handed to nginx.

The split matters because of one constraint that shapes the whole deployment:
**the SPA calls `/api/mini/*` by absolute path and has no configurable base**,
so the static files and the bot must answer on the same origin.

## Authentication is Telegram's signature, and nothing else

Every route except `/api/mini/health` requires `initData` in the
`X-Telegram-Init-Data` header (or `Authorization: tma …`), validated with
aiogram's own `check_webapp_signature` against `BOT_TOKEN`, plus a 24-hour
age cap. There is no session, no cookie and no second credential: the caller
proves who they are on every request.

Two consequences worth holding on to. A bot token *is* the API key here, so
the test bot's signatures do not validate against production and vice versa —
which is what makes two instances on one host safe, and also what makes
`/api/mini/*` impossible to share between them. And "is this person an
admin" is still `settings.is_admin(tg_id)` against `ADMIN_TG_IDS`, checked in
`_require_admin` on every admin route.

## Deploying it (this is not in CLAUDE.md yet — it should be)

Nothing about the SPA is reproducible from `git pull` alone. The shape we
settled on, on a 1 GB VPS that must never be asked to run `npm`:

```bash
# build locally — Node is deliberately NOT installed on the server
cd webapp && npm ci
npx tsc --noEmit && npx vite build --base=/app/
scp -r dist/. server:/var/www/xbox-mini/
```

`--base=/app/` is required: without it the built `index.html` asks for
`/assets/…` at the domain root, which is proxied to the bot, and the page
loads blank. On Git Bash for Windows prefix the command with
`MSYS_NO_PATHCONV=1`, or the argument is rewritten into a Windows path and
the base silently becomes `/Program Files/Git/app/`. Verify by reading the
whole `src="…"` out of `dist/index.html` — grepping for a substring will
happily match inside the mangled path, which is how that one got through the
first time.

nginx serves the files and proxies the API, on the same server block as the
OAuth callback:

```nginx
location /api/mini/ { proxy_pass http://127.0.0.1:8080; }
location = /app     { return 301 /app/; }
location /app/assets/ {
    alias /var/www/xbox-mini/assets/;
    add_header Cache-Control "public, max-age=31536000, immutable";
    gzip on; gzip_types application/javascript text/css image/svg+xml;
}
location /app/ {
    alias /var/www/xbox-mini/;
    try_files $uri $uri/ /app/index.html;
    add_header Cache-Control "no-cache";
}
```

The two cache rules are not tuning. Vite hashes every asset name, so those
are safe forever; `index.html` names the hashed assets, so a cached copy pins
a client to a build that may no longer exist — which is exactly how a fixed
deployment kept looking broken.

Finally, **`MINI_APP_URL`** in the environment. Empty means the feature is
invisible: no menu button, no entry points, slash commands unchanged. Setting
it makes the bot publish its own menu button at startup
(`_publish_mini_app_menu` in `bot/main.py`) — no BotFather step needed.

## What it costs, measured

On the production box, because the answer was not obvious with 300 MB free
and 600 MB already in swap:

| | |
|---|---|
| the code existing | **nothing** — `import bot.main` is 197.3 MB without it, 197.0 MB with |
| serving it | **nothing** — 500 signed requests moved RSS by 0.0 MB |
| per request | ~44 ms; the heaviest payload is the feed at 130–206 KB |
| on disk | 408 KB of static files |
| on the wire | 131 KB gzipped for a first open, 0.5 KB after |

It adds no process and no dependency: everything `mini_api` imports, the bot
already held. The one thing that *would* have hurt this box is building the
SPA on it, which is why we don't.

## Database and repo

Migration **049** adds `user_settings.show_secrets` — per person, off by
default, and it applies to the app only. A group post cannot hide a name from
one viewer, so nothing about published messages changed.

New repo methods, all in the existing idioms (`OWNED_BY_PERSON_EXISTS`,
`earned_at`/`earned_since` from `db/repo/_sql.py`): `person_recent`,
`chat_unlock_months`, `psn_trophy_tier_counts`, plus optional `since`/`until`
on `chat_recent` and `until` on `users_games_achievements`. The date rule is
unchanged and shared — the app windows the same way every other list does.

## The lesson from this release: 940 passing tests, two dead handlers

Both bugs that stopped the app from opening were found by *opening it*, not
by the suite:

- `psn_trophy_tier_counts` was called in two modules and defined in none, so
  `/api/mini/me` — the first request the client makes — answered HTTP 500 for
  anybody with PSN linked;
- `delete_psn_poll_state` is called in `handle_disconnect_psn` and still does
  not exist, which is why disconnecting PSN raises and takes two taps.

Python resolves an attribute when the line runs, so a call to a method nobody
wrote is invisible until someone taps that exact button. **There are no tests
that call an API handler.** This is the same failure this codebase already
recorded in 2026-09-13, when three admin buttons shipped dead because the
tests asserted the keyboard was drawn and never invoked the handler.

If you add a route here, add a test that calls it. A static check helps as a
backstop — walking every `repo.*` call in `bot/web/mini_*.py` and asking
`hasattr(Repo, name)` finds this whole class in a second — but it is not a
substitute for exercising the handler.

## Entry points, and a warning about reading dead code

The branch arrived with every way *into* the app written and connected to
nothing: six translated strings with no caller in either locale
(`chat-hub-open-app`, `chat-app-hint`, `chat-app-no-url`,
`connect-open-app-*`, `main-cmd-app`), `bot/services/mini_app.py` with four
functions nobody called, and `hub_keyboard` rebuilt as a list of rows with
no row ever appended to it.

It was read here first as leftover scaffolding — in particular a
`settings: Settings` parameter threaded into five handlers in
`bot/handlers/chat.py` and read by none, which is exactly what an abandoned
draft looks like. It was the opposite: the unfinished half of a feature
whose other half was complete, down to the SPA parsing `start_param` in
`App.tsx`. The tell was that the *strings* existed in both locales; nobody
translates what they are deleting.

Wired in 1.2.0: the hub grows an "open the app" row and `/app` answers with
the same button anywhere. **A group cannot carry a `web_app` button at
all** — Telegram answers `BUTTON_TYPE_INVALID` — so there it is a plain
`t.me/<bot>?startapp=c<chat>` link, and `mini_app_open_markup` picks the
shape. That rule is only discoverable from Telegram's own API, which tests
here may not call, so `tests/test_mini_app_entry.py` pins it instead.

`scripts/render_screen.py hub` draws the row, reading `MINI_APP_URL` through
`Settings` — not `os.environ`, which is empty for anybody running the script
the ordinary way and which briefly made the script disagree with the
production it was pointed at.

## Known open items

Tracked on the pull request, not fixed here: the missing
`delete_psn_poll_state`; the connect form's input not accepting text; toggles
not rendering their on state; no handler tests; `cors_middleware` reflecting
any `Origin`; `handle_sync` computing its window from
`presence_state.updated_at` (the same defect as issue #82, where it makes
catch-up a no-op); connect/disconnect logic duplicated in `mini_api.py`
instead of calling the services the command handlers use; and the in-process
avatar cache having no entry cap. `connect-open-app-hint` and
`connect-open-app-button` are still translated and still unused — the
connect flow never grew its own button.
